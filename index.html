SEC·01The chain — and the missing layer

Recognition and authentication answer increasingly well who the actor is and whether the expected human is present. A regulated transaction eventually needs one more answer: were they allowed to do this exact thing?

MODULE 01

Identity

Human Token
face → personId

MODULE 02

Authentication

Smart Revalidation

MODULE 03 · OPEN LAYER

Authority

mandate · scope · budget · expiry · revocation

MODULE 04

Transaction

the exact economic action that was approved

MODULE 05

Evidence

what a bank, auditor or court can verify later

KNOWING WHO THE HUMAN IS ≠ KNOWING WHAT THEY AUTHORISED. That distinction becomes more important — not less — when software or an AI agent acts for them.

SEC·02Technical Truth Map v1

The shortest version of the research. “Confirmed” means supported by reviewed public material — not production-tested.

Confirmed

Human Token is recognition

A selfie resolves to idFace.personId. The docs say identity is the output, not the input. Closer to “who is this recurring face?” than to document-first KYC.

Unknown

personId scope is the big question

Global? tenant-scoped? API-key scoped? Or a customer-facing alias of a global internal identity? Public docs do not say — and this single answer changes the privacy model of the whole product.

Confirmed

Multi Accounts asks a different question

Segmented 1:N search inside an operator's base, keyed by clientReference: “is this face already attached to another account in my segment?”

Confirmed

Documented Smart Revalidation references are not personId

The documented reference is a prior process ID or an image. Recognition identity, authentication reference and authentication event are deliberately separate objects.

Likely

Presence is a separate assurance property

Raw Base64 can enter Human Token, while Unico documents that liveness cannot be invoked through a raw-image API alone. Safest model: recognition first; live presence depends on the capture path.

Confirmed

IDPay is the concrete transaction-binding exception

General Smart Revalidation has use-case/context semantics. IDPay explicitly binds identity to order, value and card context — and adds an evidence/chargeback workflow.

Vendor claim

“Cryptographic chain of custody” needs a visible artifact

Public docs expose process records, selfie and Evidence Set PDF. They do not publicly document an RP-verifiable signed decision receipt, JWKS, signed webhook, manifest or trusted timestamp.

Do not repeat

World is not “proof with no identifier”

World ID 4.0 exposes scoped identifiers — a nullifier and an optional per-RP session ID. The real contrast is scoping/unlinkability, not identifier vs no identifier.

SEC·04Unico and World: different trust primitives

A small architectural contrast, not a ranking.

◉ Unico — provider-resolved recognisability

  • Face and provider-held state resolve the recurring human.
  • Strong fit for fraud, account continuity and adaptive re-authentication.
  • Provider can observe the reuse event.
  • Critical open question: how the RP-visible personId is scoped.

◎ World — scoped cryptographic presentation

  • User-held credentials presented through proofs.
  • RP/action-scoped identifiers and optional per-RP sessions.
  • Designed to reduce cross-RP linkability.
  • Still no general mandate object for AI-agent authority.

SEC·05Five questions I would ask

Each answer changes the architecture model. None is meant as a gotcha.

personId scope. For the same human, would two different Unico customers receive the same personId, pairwise identifiers, or does Unico maintain a global identity internally and expose customer-specific aliases?

One graph or several? Are Human Token, Multi Accounts and network-history fraud signals ultimately resolving against the same underlying biometric identity graph, or deliberately separate namespaces/stores?

Recognition vs presence. Since raw Base64 can enter Human Token on a path where the documented liveness capability is not available, should personId be understood primarily as face recognition, while live-presence assurance is a separate property of the capture path?

Transaction evidence. What exactly is the technical artifact behind “cryptographic chain of custody”? Can an RP verify a signed object binding authentication event + transaction parameters + time + policy/version, or is that provenance currently maintained inside Unico?

The next layer. You already solve “who is this human?” and increasingly “is this the same human acting now?”. How are you thinking about proving that this human — or an AI agent acting for them — had authority for this exact action under a specific mandate?

SEC·06Five sandbox tests

Not attack testing — small, consented experiments ordered by information gain.

X1 · STABILITY

Repeated + cross-channel capture

Same person, different days/devices; API vs SDK/Web. Tests stability, channel consistency and presence semantics.

X2 · NAMESPACE

Two keys / branches

Same tenant, same human, different API keys/segments/branches. Tests the inner namespace boundary.

X3 · HIGHEST VALUE

Two tenants

Same human under an explicitly permitted two-tenant test. Distinguishes global RP-visible ID from scoped aliasing.

X4 · CROSSING

Human Token ↔ Multi Accounts

Run both in both orders to learn whether product state crosses the boundary.

X5 · FORENSICS

Revalidation + PDF forensics

Compare use cases and silent/facial paths; inspect Evidence Set for signatures, timestamps, manifests and bindings.

SEC·08Where I think I could be useful

My interest is not another biometric matcher. It is the layer that turns identity and authentication into accountable authority inside regulated financial systems.

AREA·01

Authority / mandate model

A machine-readable object linking principal → human/agent delegate → scope → budget → validity → revocation, rather than treating successful authentication as permission.

AREA·02

Decision receipt

A durable, signed receipt binding identity evidence, authentication event, mandate and transaction digest — independently verifiable later by a regulated third party.

AREA·03

Privacy-preserving interoperability

Combine Unico-style recognisability and fraud utility with pairwise/scoped identifiers, so reuse does not automatically create a cross-RP biometric join key.

AREA·04

Experiment harness

A small reproducible sandbox suite that converts architecture UNKNOWNs into measured results instead of relying on product prose.
